# ADR 0014: Evaluation design: a committed fixture, hand-written gold, an independent leak oracle, a judge from another model family

Status: accepted (2026-09-22)

## Context

The README promises retrieval quality, grounded answers and no entitlement leaks. None of
that is provable from unit tests, which stub the index and the model. CI has no model
available, so any suite that needs one cannot run there, and a suite that runs only locally
is easy to skip before a merge.

## Decision

**The fixture is the full corpus at full precision, with question embeddings precomputed.**
`sovrag eval build-fixture` reads the live index and writes `eval/fixture/`: every document
and chunk, the chunk embeddings as little-endian float32 (the same encoding pgvector stores),
and an embedding for every question in the three golden files. `sovrag eval load-fixture`
loads that directory into any Postgres, needing no model. CI runs `load-fixture` then the
retrieval and leak suites against it, reading `questions.f32` instead of calling an embedder,
so CI measures the index users actually query, not a stand-in.

**Golden items are written from chunk text, keyed by `(doc_id, ordinal)`, never from
retrieval output.** A person reads a chunk directly and writes the question, the gold chunk
reference and, for `retrieval.jsonl`, a reference answer in the chunk's own words. Grading the
retriever against what the retriever itself returned would make every suite pass by
construction; `(doc_id, ordinal)` survives a re-ingest, unlike the `chunks.id` serial.

**The leak oracle is an independent Python statement of the visibility rule.** `sovrag.eval.
leak.visible` restates ADR 0013's rule rather than importing `sovrag.retrieve.filters`, and a
test asserts the two agree for every named principal. An oracle built from the same predicate
it is meant to check would inherit that predicate's bugs and catch nothing.

**The judge is a different model family from the generator, and a run refuses a judge equal
to the generator.** The default judge is Gemma 4 12B (`ai/gemma4:12b-q4_K_M`) against a
Qwen 3.5 9B generator, so the judge does not share the generator's blind spots. `sovrag eval
generation` raises before making a call if `Settings.judge_model` is unset or equals
`Settings.llm_model`.

**Every result carries model tags, `engine` and `engine_backend`, and thresholds may only
rise.** Each file under `eval/results/` records `embed_model`, `llm_model`, `judge_model`,
`engine` (default `docker-model-runner`) and `engine_backend` (default `llama.cpp`), so a run
on a different quantization or backend is never mistaken for this baseline. `eval/thresholds.
json` gates the retrieval and leak suites in CI; a pull request may raise a threshold but
never lower one.

## Consequences

- The fixture adds about 14 MB of binary to the repo (`eval/fixture/chunks.f32` is the bulk of
  it), regenerated by one command and never hand-edited; `.gitattributes` marks it generated
  and excludes the `.f32` files from diffs.
- HNSW is an approximate index, so the retrieval and leak suites see slightly different
  results run to run; thresholds sit a small margin below the measured baseline for that
  reason and are checked, not chased.
- The generation suite needs a live model and a judge, so it runs locally, not in CI, and its
  numbers are labelled by the model, quantization and backend they were measured on rather
  than presented as a fixed target.
- A full-precision run on vLLM, or a run against a different generator or judge, is a settings
  change plus a new result file; the harness makes that comparison possible but does not run
  it here.
