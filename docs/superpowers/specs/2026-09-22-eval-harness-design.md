# Evaluation harness: retrieval, generation and leak suites

Date: 2026-09-22. Status: draft for review.

## Goal

`sovrag eval` measures the three things the README promises and the code cannot prove about
itself: that retrieval finds the right chunks, that answers are faithful to what they cite, and
that a principal never retrieves a chunk they are not entitled to. The retrieval and leak suites
are deterministic and run in CI against a committed index. The generation suite needs a live
model and a judge, so it runs locally and its results are committed with the model and
quantization they were measured on.

## Layout

```
src/sovrag/eval/            code: metrics, golden loading, fixture build and load, three runners
  __init__.py
  metrics.py                pure: hit_at_k, recall_at_k, mrr, over (doc_id, ordinal) keys
  golden.py                 dataclasses and loaders for the three golden files
  fixture.py                build (from the live index) and load (into any index)
  retrieval.py              retrieval suite runner
  generation.py             generation suite runner and judge prompt
  leak.py                   leak suite runner
  report.py                 result envelope: models, engine, commit, metrics, rows
eval/golden/                hand-written truth, never generated
  retrieval.jsonl           30 answerable questions with gold chunks and a reference answer
  unanswerable.jsonl        10 questions the corpus cannot answer
  leak.jsonl                20 questions answerable only from protected departmental or OAG documents
eval/fixture/               generated by `sovrag eval build-fixture`; marked generated, never hand-edited
  manifest.json             embed model, dim, counts, sha256 of each file, build timestamp
  documents.jsonl           one row per document, the same columns as the documents table
  chunks.jsonl              one row per chunk: doc_id, ordinal, heading_path, text
  chunks.f32                embeddings, little-endian float32, row-major, in chunks.jsonl order
  questions.jsonl           question id and text, for every question in the three golden files
  questions.f32             their embeddings, same encoding
eval/thresholds.json        CI gates for the retrieval and leak suites; values may only go up
eval/results/               committed runs, one file per suite and date
```

Golden files reference chunks as `(doc_id, ordinal)`, never by the `chunks.id` serial, because
ids change on every ingest and ordinals are fixed by the deterministic chunker.

The fixture is the full corpus at full precision. pgvector stores `vector(1024)` as 4-byte
floats, so float32 is exactly what the live index holds and CI measures the same index users
query. The embeddings file is about 13.8 MB; that size was accepted over a half-precision or
subset fixture because the eval exists to answer questions about the real index.

## Golden sets

Every item is written by a person reading chunk text directly, document by document, never by
taking what retrieval returns first. Writing gold from the retriever's own top hit would make
the eval grade the retriever against itself. Each item records the chunk that was read.

`retrieval.jsonl`, 30 items, at least one per document:

```json
{"id": "r01", "question": "...", "gold": [{"doc_id": "dnd-dp-2025-26", "ordinal": 14}],
 "reference_answer": "one or two sentences, in the words of the chunk", "notes": "why this chunk"}
```

`gold` may list more than one chunk when the answer spans two. `reference_answer` is used by the
generation suite.

`unanswerable.jsonl`, 10 items: questions on the corpus's topics whose answer is not in any
document (a fiscal year the corpus does not hold, a department not in the corpus, a figure the
reports do not state). Fields: `id`, `question`, `notes`.

`leak.jsonl`, 20 items: questions answerable only from the 13 protected documents (10
departmental results reports, 3 Auditor General reports), at least one per document. Fields:
`id`, `question`, `gold` as above. The forbidden set for a principal is not stored; it is derived
at run time from the visibility rule (see the leak suite below), so the suite tracks the rule.

The author drafts all 60 items; the user spot-checks ten before they are treated as truth. Both
facts go in the pull request.

## Suites

### Retrieval (CI)

For each `retrieval.jsonl` item, for each mode, search as `auditor` (who sees every document)
with `k = 10`, passing the precomputed question embedding as `embed_query`, so no model runs.
Metrics per mode: hit@5, recall@10 and MRR at chunk level, plus hit@5 at document level.
Reported per question and averaged. Runs in CI after `sovrag eval load-fixture` fills the
service Postgres; the averages are compared to `eval/thresholds.json` and the job fails below
them.

HNSW is an approximate index. The suite calls the same `search` functions users do, with the
same `ef_search` behaviour, so the numbers describe the real query path rather than an exact
scan. Thresholds are set a small margin below the measured baseline for that reason, and a pull
request may raise a threshold but never lower one.

### Leak (CI, plus a local answer check)

For each `leak.jsonl` item and each of the five named principals, search in all three modes with
`k = 10` and assert that no returned chunk belongs to a document the principal may not see.
Forbidden documents are those the visibility rule excludes for that principal. The suite
computes them with its own Python statement of the rule over the `documents` table, independent
of the SQL predicate in `sovrag.retrieve.filters`, and a test asserts the two agree for every
named principal. An oracle that reused the predicate would inherit its bugs. This check is exact
and is the CI gate: any forbidden chunk fails the job.

Positive control: the same questions searched as `auditor` must return at least one gold chunk
in the top 10 in hybrid mode for at least 18 of the 20 items, so the suite cannot pass by asking
questions nothing answers. The 18 is in `thresholds.json` with the others.

Locally, with a model available, the suite also calls `answer()` for each item as `public`,
`analyst_dnd` and `analyst_ps` and reports how many refused. This is reported, not gated,
because the generator may legitimately answer a leak question from visible material that
overlaps it.

### Generation (local)

For each `retrieval.jsonl` item, call `answer()` as `auditor` in hybrid mode with `k = 5`.
Then the judge scores the answer from the question, the cited chunk texts and the reference
answer, and returns JSON:

```json
{"faithful": true, "unsupported_claims": [], "correct": "yes"}
```

`faithful` is false when any claim in the answer is not supported by the cited chunks;
`correct` is `yes`, `partial` or `no` against the reference. The judge is called through the
same `Generator` class as the generator, with `Settings.judge_base_url` and
`Settings.judge_model`, at temperature 0. The judge must be a different model family from the
generator so it does not share its blind spots: the default is Gemma 4 12B (`ai/gemma4:12b-q4_K_M`),
set in `.env.example`. A run refuses to start if the judge model equals the generator model.

For each `unanswerable.jsonl` item, call `answer()` the same way and record whether it refused.

Reported: faithfulness rate, correctness distribution, refusal rate on unanswerable items,
refusal rate on answerable items (false refusals), and latency per call. How often the uncited
retry fires is not observable from `Answer` or the audit line today and is not reported. Ten judged answers, chosen by a fixed seed, are listed
in the result file with an empty `human_check` field for the user to fill; the agreement rate
between the judge and the human is reported once filled, by `sovrag eval agreement <result file>`.

## Result files

Every suite writes one JSON file to `eval/results/<suite>-<YYYY-MM-DD>.json`:

```json
{"suite": "retrieval", "ran_at": "...", "commit": "abc1234",
 "embed_model": "hf.co/gpustack/bge-m3-gguf:Q8_0",
 "llm_model": "ai/qwen3.5:9b-q4_K_M", "judge_model": "ai/gemma4:12b-q4_K_M",
 "engine": "docker-model-runner", "engine_backend": "llama.cpp",
 "metrics": {...}, "rows": [...]}
```

The model tags carry the quantization, and `engine_backend` names the runtime, so a Q4 GGUF on
llama.cpp is never presented as the same generator as full precision on vLLM. Both labels are
settings (`Settings.engine`, default `docker-model-runner`; `Settings.engine_backend`, default
`llama.cpp`) because the OpenAI-compatible API does not report them.

## CLI

A `sovrag eval` command group:

- `sovrag eval build-fixture` reads the live index and the golden files, embeds every question
  once, and writes `eval/fixture/`. Requires the embedding model.
- `sovrag eval load-fixture` loads `eval/fixture/` into the configured database, replacing the
  documents and chunks it names. Requires nothing but Postgres.
- `sovrag eval retrieval`, `sovrag eval leak`, `sovrag eval generation` run a suite, print the
  summary, and write the result file. `--out` overrides the path. `retrieval` and `leak` take
  `--check` to compare against `thresholds.json` and exit 1 on a miss.

## CI

`ci.yml` gains, after pytest: `uv run sovrag eval load-fixture`, then
`uv run sovrag eval retrieval --check` and `uv run sovrag eval leak --check`. The fixture load
needs no model; the two suites read `questions.f32` for embeddings.

## Settings and dependencies

`Settings` gains `engine: str = "docker-model-runner"` and `engine_backend: str = "llama.cpp"`. `judge_*` already exist; `.env.example`
gets `JUDGE_BASE_URL`, `JUDGE_MODEL=ai/gemma4:12b-q4_K_M`. No new dependencies: float32 files
are read and written with the standard `array` module.

## Tests

- `tests/test_eval_metrics.py`: hit@k, recall@k and MRR against hand-computed values, including
  no gold found, gold beyond k, and two gold chunks with one found.
- `tests/test_eval_golden.py`: loaders reject a missing field, a duplicate id, and a gold
  reference to a document not in the manifest.
- `tests/test_eval_fixture.py`: build then load round-trips documents, chunks and embeddings
  exactly (float32 equality) through a test database; manifest sha256 mismatch is an error.
- `tests/test_eval_retrieval.py`: with a seeded test database and a fake embed lookup, the
  runner produces the expected metrics for a two-question golden set.
- `tests/test_eval_leak.py`: the forbidden set for each named principal matches the visibility
  rule; a seeded forbidden chunk makes the suite report a leak; the positive control counts.
- `tests/test_eval_generation.py`: with a fake generator and a fake judge, the runner parses
  the judge JSON, records refusals, and refuses to run when judge equals generator.
- `tests/test_cli.py`: `sovrag eval retrieval --check` exits 1 below threshold.

## Out of scope

Reranking, embedding model comparison, and a full-precision run on vLLM are all things this
harness makes possible and none are built here. The HTTP API follows this branch.
